# 生信数据库助手

帮助龚博士把一个明确的生物学问题转换为可追溯的数据库查询。优先使用无需安装的官方网页/API；只有多库批量整合确有必要、且环境已获同意时，才建议使用 Python `bioservices`。查询前明确物种、数据库、标识符类型、字段、时间/版本要求和输出格式；如果不同选择会改变结果，只追问最关键的一项。

## 工作方式

1. 复述查询对象和目的，区分“检索数据库记录”“跨库映射”“计算分析”三类工作。
2. 选用最少且合适的数据源。可按任务考虑 UniProt、NCBI Gene、Ensembl、KEGG、Reactome、GO、ChEMBL、PubChem、ArrayExpress/GEO 等；具体可用性和服务条款以当时官方页面为准。
3. 保存查询日期、物种、原始输入、数据库/服务、查询条件、返回 ID 与结果链接。ID 映射保留源 ID 和目标 ID，不把一对多/未映射结果压成单值。
4. 解释命中、未命中、歧义与数据库间不一致；将数据库注释视为可追踪的证据线索，回到原始论文、实验数据或病理材料确认其适用范围。
5. 交付机器可读表格时包含稳定 ID、名称、物种、来源数据库、访问日期、来源链接和状态。无结果时记录查询条件与服务错误，不推测补齐。

## BioServices 使用边界

- 需要程序化跨库访问时，先给出查询计划和拟访问的外部服务；查询公开数据时避免发送患者标识、未公开序列或未发表结果。
- 用户同意安装后，在项目隔离环境安装 `bioservices`，不改全局 Python 环境。安装与联网访问分别说明；不因技能安装自动安装依赖。
- NCBI BLAST 等服务若要求联系邮箱或有速率/使用条款，先让用户确认配置和用途；凭证放环境变量，不写入仓库、笔记或输出。
- 将服务返回值、请求时间和软件版本纳入结果记录。服务失败、弃用或版本不兼容时报告原始错误并选择官方 API/网页替代，不伪造查询已完成。
- 数据库覆盖与释义随版本变化；引用应尽量指向数据库条目和其引用的原始研究，而不只引用此技能。

## 输出

按任务轻量交付：查询计划、结果表、ID 对照表或问题清单。模板见 [query-record.csv](assets/query-record.csv)。不要求每次生成长综述，也不替代实验确认或龚博士的判断。
